# k3s 规模化商用就绪度评估

**评估日期**：2026-09-05
**方法**：全部结论来自对运行中集群的实测，不引用文档声称
**结论**：**适合内部/试点，不适合对外商用承诺 SLA**

---

## 0. 一句话总结

工程实践（GitOps、供应链、可观测）做得**超出这个规模的常见水平**，
但**基础设施拓扑决定了拿不出可用性承诺** —— 4 个 1-vCPU 节点、
31 个单副本服务、全部数据锁在节点本地盘。

★这不是「哪里没做好」的问题，是**当前架构的能力上界**。
要签 SLA 得先改拓扑，不是补配置。

---

## 1. 做得好的（有实测支撑）

| 维度 | 证据 |
|---|---|
| **PG 备份** | 每小时 barman → OCI，`completed`；可恢复窗口回溯至 2026-08-06 |
| **Vault 备份** | 每日 raft 快照（本轮新建），端到端实测 72320 字节、回读一致 |
| **告警链路** | 143 条规则；Slack 22 次 + Telegram 22 次投递，**失败 0 次** |
| **证书自动化** | 14/14 Certificate `Ready`，cert-manager 自动续期 |
| **供应链** | 9 个镜像全 digest pin + cosign 验签 + CIP 准入（本轮补完） |
| **GitOps** | 全部应用 ArgoCD 管理；分支保护 + 逐 PR 门禁 |
| **Pod 安全** | 52 个容器中 48 个强制 `runAsNonRoot`（93%） |
| **资源治理** | 81% 容器设了 requests/limits |

## 2. 阻断商用的三个硬缺口

### 2.1 ★没有任何高可用（最根本的一条）

```
31 个单副本服务   vs   4 个多副本
```

单副本的包括**整条控制链**：`argocd-server`、`argocd-application-controller`、
`cert-manager`、`cnpg-system/cloudnative-pg`、`authentik-server`、
`cloudflared`（唯一的入口隧道）、`vault`、`shared-postgres`。

**具体后果**（按节点算）：

| 节点挂掉 | 直接影响 |
|---|---|
| master-2 | **PG + Vault 同时不可用** → 全平台密钥与业务库双失 |
| worker-1 | Tempo、ckeditor 不可用（14 个 Pod） |
| 任一节点 | 该节点上 10-14 个 Pod 全部不可调度（数据绑死本地盘） |

★`cloudflared` 单副本尤其致命：它是**唯一的公网入口**，
挂了等于整站不可达，与后端有几个副本无关。

### 2.2 ★数据全部锁在节点本地盘

全部 8 个 PV 都是 `local-path`，带 nodeAffinity：

```
master-1  Prometheus 5Gi + Grafana 2Gi
master-2  PG 20Gi + Vault data 10Gi + Vault audit 5Gi   ← 最关键
master-3  Redis 2Gi
worker-1  Tempo 5Gi + ckeditor 1Gi
```

Pod **无法漂移** —— 节点故障时 K8s 的自愈完全失效，
不是「慢一点」而是「起不来」。

★并且存在**超额认领**：master-2 上 PV 声明合计 35Gi，
而该节点根盘只有 29.4G（剩 6.5G）。`local-path` 不预留空间，
所以现在没事，但 PG 长到 ~7G 时会**节点级磁盘耗尽**，
波及该节点上的所有服务 —— 详见
`2026-09-05-block-volume-migration.md`。

### 2.3 ★容量已接近上界，且无法横向扩

```
节点规格   1 vCPU / 5.6GB × 4
CPU requests  master-1 55%  master-2 80%  master-3 83%  worker-1 75%
根盘使用      78% / 78% / 79% / 85%
```

CPU requests 已占 55-83%。**1 vCPU 的节点连"给关键服务加一个副本"
都很勉强** —— PG 加一个副本约需再占 100-200m，master 已到 80%+。

实测证据：`CPUThrottlingHigh` 正在 firing ——
`authentik/worker` 被节流 **66.64%** 的时间。这不是预测，是当前状态。

## 3. 次级缺口（不阻断，但商用前应补）

| 缺口 | 现状 | 影响 |
|---|---|---|
| **东西向隔离** | **全集群仅 1 条 NetworkPolicy** | 任一 Pod 被攻破可横向访问全部服务 |
| **配额约束** | ResourceQuota=0、LimitRange=0 | 单个失控工作负载能拖垮整个节点 |
| **etcd 备份** | 未见备份任务 | k3s 控制面状态丢失需从头重建集群 |
| **恢复演练** | 从未做过 | **备份没验证过恢复 = 不知道有没有备份** |
| **凭据归属** | 备份 key 挂在**个人账号**下 | 人员变动直接断掉备份链路 |
| **Vault seal** | unseal key 与密文同集群 | 拿到 etcd 快照即拿到密钥（已知取舍） |

★**东西向隔离那条最值得优先**：1 条 NetworkPolicy 意味着
`kube-router` 层面几乎完全放通。对外商用时，
「一个应用被攻破 = 整个集群被攻破」是很难向客户解释的。

（注：本仓有过 kube-router 处理含 podSelector 的 NetworkPolicy 的 bug，
故补隔离需先验证 CNI 行为，不能直接照搬通用模板。）

## 4. 分场景结论

| 场景 | 结论 | 理由 |
|---|---|---|
| **内部开发/演示** | ✅ 完全够用 | 现有工程实践质量高于多数同规模环境 |
| **小规模试点**（可容忍分钟级中断，不签 SLA） | ⚠️ 可以，但需先补 §3 前三项 | 单点故障需明确告知用户 |
| **对外商用 + SLA** | ❌ 不可 | §2 三条都是架构级，配置层面补不了 |
| **合规/审计场景** | ⚠️ 部分就绪 | 供应链与审计做得好；但缺东西向隔离、无恢复演练 |

## 5. 若要走向商用：改造路径

按**性价比**排序，不是按理想架构排序。

### 阶段一：低成本、立竿见影（不改拓扑）

1. **cloudflared 加副本** —— 唯一入口单点，加副本几乎零成本
2. **补 NetworkPolicy** —— 先做 namespace 级默认拒绝，逐个放行
3. **加 ResourceQuota / LimitRange** —— 防单个负载拖垮节点
4. **配 etcd 定期快照** —— k3s 原生支持，配置项而已
5. **做一次恢复演练** —— 独立环境验证 PG + Vault 快照真能恢复
6. **建专用 IAM 服务用户** —— 把备份凭据从个人账号剥离

★这六项都**不需要停机、不需要加机器**，是当前最该做的。

### 阶段二：需要加资源（改拓扑）

7. **节点升配**：1 vCPU → 2-4 vCPU。这是**所有 HA 方案的前提** ——
   当前规格下加副本只会让节流更严重
8. **PG instances=2** —— 升配后才有意义
9. **引入网络存储**（Longhorn / OCI CSI）—— 让数据脱离节点，
   这是「Pod 能漂移」的前提，也是真正 HA 的分界线
10. **关键控制面组件加副本**（ArgoCD、cert-manager、authentik）

### 阶段三：真正的 HA

11. **Vault 3 副本** —— ★注意：**不要 2 副本**。Raft 需奇数节点，
    2 副本 quorum=2 → 挂任一台整个 Vault 不可用，**比单副本更差**
12. **多 AD 部署** —— 当前 4 节点全在 AD-1，AD 级故障全灭
13. **定义并测量 SLO** —— 有了冗余才谈得上承诺

---

## 6. 成本现实

★必须说清楚：**§5 阶段二之后的每一步都要花钱**。

用户选择自建 k3s 的动机正是避免托管费用。
节点升配、网络存储、多 AD —— 都是持续性成本。

**故本评估的建议是**：先把阶段一六项做完（零成本、纯收益），
然后**根据实际商用需求**决定是否投入阶段二。
在没有付费客户之前，为假想的 SLA 提前买单是不划算的。

★「当前架构撑不起商用 SLA」与「现在就该改架构」是两个问题。
前者是事实，后者取决于商业进度。

---

## 7. 本评估的局限

- 未做压力测试，容量结论基于 requests 占比与节流告警，非实测吞吐
- 未验证恢复流程（这本身是 §3 列出的缺口）
- 未评估应用层（aster-api 等）的代码质量，只看基础设施
- 单点故障影响面基于 Pod 分布推断，未做实际的节点故障演练
